#### ③ ⚠️ 勘误：旧记录「**疑为 6bit 面板**」**不成立**

| | |
|---|---|
| **原判定** | `.paper/01` §1 ＋ mydrivers 评测：「**疑为 6bit 面板**」 |
| **现判定** | ❌ **错误** —— ★ **EDID `byte20` 明确声明 `8 bit/基色`**（bits 6-4 = `010`）<br/>＋ **屏库规格书写 `16.7M (8-bit)`** ⇒ **两个独立来源都是 8 bit** |
| **原判定为何产生** | 评测方大概是**从可视角度/色域表现反推**的（6bit+FRC 的屏常有这类表现）—— ★ **外观反推不可靠** |
| **影响** | 无功能影响（本项目不依赖色深）；但**升级路径若考虑 HDR，8bit 仍是硬门槛**（见 ④） |

#### ④ ★★★★ HDR：**四重否定** ⇒ **不支持 HDR**

| 要件 | HDR10 需要 | 本面板 | 判 |
|---|---|---|---|
| **色深** | 10 bit | **8 bit**（EDID ＋ 规格书**双证**） | ❌ |
| **峰值亮度** | 高（DisplayHDR 400 是**最低档**，公认"不算真 HDR"） | **400 nit (Typ.)** | ❌ |
| **对比度 / 控光** | 高对比 或 **分区控光** | **1000:1 ＋ 侧入式 WLED，无分区** | ❌ |
| **接口申报** | EDID 要有 CTA-861 HDR 静态元数据块 | ★ **EDID 扩展块 = 0** | ❌ |

> ★★★ **差点被骗过去的一处**：平台 `Display.getHdrCapabilities()` 对这块屏报
> **`HDR=true, 类型=[HDR10/HLG]`, 峰值 500.0 nit** —— **看着板上钉钉，其实是平台的默认回落值**。
> 两条独立反证：① **`500.0` 在 CTA-861 的 `50·2^(c/32)` 编码里根本无法表示**（`c≈106.3` 非整数）；
> ② 手机内置 AMOLED 与 TNT GO 的 INX **报的峰值是同一个 `500.0`**。
> ★★ **教训：「系统说它支持 X」≠「硬件真的支持 X」；能力类结论要追到【申报方】的原始字节。**

#### ⑤ ★★ 两条结构性事实（对项目有实际意义）

| # | 事实 | 意义 |
|---|---|---|
| **1** | **面板原生接口 = eDP 4 Lane / eDP 1.3**，而手机侧走 **DP Alt Mode** | ⇒ ★ **TNT GO 内部有 DP→eDP 桥接芯片**（USB 树里那颗 **Analogix `1f29:0000`**）<br/>⇒ **我们读到的 EDID 是【桥】报的**（桥的固件写入了面板型号/参数）<br/>⇒ ★ **这也解释了为什么调背光走 AT 命令台而不是标准 DP 亮度控制** —— 背光归桥/MCU 管 |
| **2** | 背光 **WLED 9S6P / 6 串 / 侧入式** | ★ **无分区控光（FALD）** ⇒ HDR 的第三条路也堵死 |

#### ⑥ ⚠️ 用户 2026-09-13 的定性（**一半已证、一半无据，分开记**）

> 用户：「亮度范围我们暂时不管了，这块屏**能支持 HDR 信号**，但其亮度估计也就在
> **400-500 nit** 左右，其**最多是一块支持 HDR 信号的屏幕**」

| 分句 | 判定 |
|---|---|
| **亮度 ≈400 nit** | ✅ **已证（两源吻合）** |
| ⚠️ **"到 500 nit"** | ❌ **无支撑** —— ★ **500 极可能就是那个平台默认值**（本 §④ 已否掉） |
| ★★ **"能支持 HDR 信号"** | ⚠️ **本工作区无证据支持，且现有三条证据都反向**：<br/>① EDID 扩展块 = 0（接收端没申报 HDR）② EDID 声明 8bit ⇒ 内核按此配 `24bpp` ③ **DPCD 报 `DP 1.1`**（DP 侧 HDR 元数据标准化传输是 DP 1.4 / CTA-861.3） |
| ★ **"最多是一块支持 HDR 信号的屏幕"** | ✅ **方向正确** —— 无论如何**都不是真 HDR** |

> ★★ **一条【推断，未实测】的反向风险**：平台的 `HdrCapabilities` 默认值说它支持 HDR10/HLG，
> 而 **Android 正是拿这个值决定"要不要发 HDR 信号"** ⇒ **系统有可能真的给它发 HDR10**，
> 而接收端并不认 ⇒ **推测后果：HDR 内容在 TNT GO 上可能颜色发灰/过曝**。
> **⇒ 本项目实用结论：不要为 TNT GO 规划任何 HDR 功能**；HDR 属于**小米端**的显示管线。
> ### ✅ **2026-09-13 已实测结清（见 §1.1.1）—— 上条推断被否定：手机上根本没有向它发 HDR**

#### ⑥-b ★★★★★ 实测：**手机发给 TNT GO 的是 SDR 还是 HDR 信号？→ 始终是 SDR 8-bit**

> **详档**：[`.ref/Search-Results/01` §1.4](../.ref/Search-Results/01-tnt-go-hardware.md)
> **方法**：用 ffmpeg 造一段**真 HDR10**（HEVC Main10 / `smpte2084`(PQ) / `bt2020` ＋母版显示元数据），
> 推入设备 MediaStore，**点名锤子播放器播到 TNT 屏**，然后逐层观测。

| 环节 | 观测 |
|---|---|
| **解码器** | `E OMX-VDEC-1080P: …describeHDR10PlusInfo not implemented` ⇒ ★ **认出了 HDR** |
| ★★ **SurfaceFlinger 层** | `dataspace=BT2020_ITU_PQ (298188800)`　`hdr metadata types=3` ⇒ **真 HDR10 层** |
| ★★ **合成器(SDM)** | `Supported color mode count = 1` / `Color mode = 0 (NATIVE)` ⇒ **该屏没有 HDR 模式** |
| ★★★ **DP 链路** | `2160(…)×1440(…)@60fps **24bpp** …` —— ★ **播放 HDR 前后都是同一行，<br/>所有 `_dp_panel_calc_tu` / `link_train` 时间戳都停在连接那一刻** ⇒ **链路从未重配** |

**⇒ 结论：即使播放真 HDR10，输出端也【没有变成 HDR】——
HDR 内容在手机侧被转换/色调映射成 SDR 后才发出去。**

**四层结构性原因（任何一层都足以否掉"发 HDR"）**：
① 接收端**没申报 HDR**（EDID 扩展块 = 0）② 接收端**申报 8-bit** ⇒ 链路 `24bpp`，<br/>
③ 接收端是 **DP 1.1**（DP 侧 HDR 传输是 DP 1.4 / CTA-861.3）④ **合成器只有 1 种 color mode**。

> ★★ **这实测否定了"能支持 HDR 信号"的假设** —— 至少本机这条通路，**手机从未发出过 HDR 信号**。
> ⚠️ **实验边界**：测试片是"**SDR 码值 + PQ 标签**"，所以**只能证明信令与链路**，
> **证明不了色调映射的质量**（要验那个得用 `zscale` 真正转 PQ 码值）。
> ★ **实用含义**：在 TNT GO 上看 HDR 片源 = **走一遍 HDR→SDR 转换**，画质不会更好，**可能更差**。

## 3. USB 复合结构

TNT GO **不是单一 USB 设备**,而是「**1 个 USB 2.0 Hub + 3 个下游功能器件**」:

```
usb 1-1    0424:2514   Microchip USB2514B USB 2.0 4 口 Hub
 ├─ usb 1-1.1  1f29:0000  Analogix "USB Type-C Digital AV Adapter"(Billboard 类)
 ├─ usb 1-1.2  0bda:0567  Realtek UVC 摄像头(linux-hardware 记录为 "WEB CAMERA M9 Pro")
 └─ usb 1-1.3  31ce:5101  Smartisan 主控(full-speed)
```

### 芯片角色

| 芯片 | 判定 | 依据 |
|---|---|---|
| **0424:2514** | Microchip/SMSC USB2514B —— USB **2.0** 4 口 Hub | Microchip 产品线 |
| **1f29:0000** | Analogix DP RX 桥接器;USB class **11-00-00 = Billboard Device Class** | `linux-hardware.org/?id=usb:1f29-0000`;Analogix 产品线中 **ANX7518**(DP1.4 4-lane RX / HDMI 2.0b TX / PD3.0 / 双 CC / USB2.0 Billboard)形态吻合 |
| **0bda:0567** | Realtek UVC 摄像头(标准 uvc_driver) | `linux-hardware.org/?id=usb:0bda-0567` |
| **31ce:5101** | Smartisan 主控(HID/CDC-ACM/vendor/audio) | 实测 |

> **关键**:Billboard 类是「无法输出视频时向主机自报故障」的设备类。
> **DP 视频链路不经过该 hub** —— hub 只服务 USB 2.0 外设,DP 是独立链路。

### 主控提供的接口

> ⚠️ **勘误(2026-09-11 任务 G)**:下表原列有「**255/255/0 厂商自定义接口**」——
> **实机核实该接口不存在**。当前 TNT GO 的**全部 10 个接口**里**没有 class 255**
> (`dumpsys usb` + sysfs 双证),整台设备**只有一个 USB 配置**。
> TNT 的厂商控制传输实际发给的是**另外两个独立 USB 设备 `29A9:9001/9002`**
> (`TNT_USB_VENDOR_ID=0x29A9`),而**本机总线上没有 `29A9`** ⇒ 见 §7.1。

| 接口 | class/sub/proto | 说明 |
|---|---|---|
| 0 | 1/1/0 | HID 键盘 |
| 1 | 1/2/0 | HID 鼠标/触控板 |
| 2 | 1/2/0 | 第二 HID(多点触控) |
| 3 | 1/2/0 | HID |
| 4 | 3/1/2 | HID(Boot) |
| 5、6 | 3/0/0 | HID generic |
| **7** | **2/2/1** | **CDC-ACM 串口** ★ **AT 命令台** |
| **8** | **10/0** | **CDC-Data** ★ |
| ~~—~~ | ~~255/255/0~~ | ❌ **不存在**(勘误) |

### `dfp_send_uvdm` 是什么
- **UVDM = Unstructured VDM**(PD VDM type 位 = 0,区别于 Structured VDM)
- 协议定义:Linux `drivers/staging/typec/pd_vdo.h`
- **在多个公开 LineageOS 内核树中检索不到 `uvdm` 字符串** → 属 **OEM 私有 PD 实现**
- 语义推断(未证实):DFP 在 PD 合约建立后发厂商自定义消息,用于识别"对端是 Smartisan 显示器 / 应进入 TNT 模式"。机制与 Samsung DeX 靠 VDM 握手识别 Dock 同类。
- **载荷与触发条件未公开**

### 复刻要点
必须做 **PD Source**(非 5V 直供),且**支持 UVDM 收发**。

>
> **实测**:路线 A 显示 **27~28%** 时,路线 C 的真实值是 **100%**。
>
> **机理**:路线 A **只积分「消耗」**(`dmesg healthd` 的 `iv×ic` 累加),
> **TNT GO 被外部充过电时它不回补** ⇒ 误差**只增不减** ⇒ **单向漂移,越用越偏**。
> 「±10%」的标称精度是**只在「满电 reset」同步点刚过时**成立;同步点越远,偏得越多。
>
> **⇒ 教训(通用)**:任何**只累加、不回归**的估算模型**必然漂移**。
> **有真实数据源时,不要用估算。**(此处真实数据源 = `at+batcg`,见路线 C)
>

+BATCG=<1电压mV>,<2电量%>,<3状态>,<4电流mA>,<5温度×0.1°C>,<6?>
```

★ **温度 = 第 5 字段 ÷ 10**（单位 °C）。判定有**两条互相独立**的依据：

| 依据 | 内容 |
|---|---|
| **原始判定**（2026-09-11 任务 I） | 两组合独立样本：`+HRM` 第 2 字段与 `+BATCG` 第 5 字段同步（差 0.1–0.5 °C）；且与 `AT+TEMP` 的 `tmp2=304` 吻合 |
| ★★ **现场复核**（2026-09-15） | **同一帧、连续 15 组样本，逐对相差 ≤ 0.1 °C** |

**现场复核（2026-09-15 18:22–18:29,坚果 Pro 3,放电中,节选）**：

| 时刻 | `+HRM` 第 2 字段 | `+BATCG` 第 5 字段 | 差 |
|---|---|---|---|
| 18:22:59 | 335 | 336 | −1 |
| 18:24:29 | 337 | 336 | +1 |
| 18:26:59 | 336 | 337 | −1 |
| 18:29:59 | 337 | 337 | **0** |

**15/15 全部落在 ±1 个最小单位（0.1 °C）内** ⇒ ★★ 比 2026-09-11 的两组样本强得多：
**同帧、连续、同设备、同一段放电过程**。

#### ② 实测范围

| 场景 | 温度 |
|---|---|
| 轻度使用（放电中） | **29.4 – 30.3 °C** |
| 持续放电数小时 | **33.6 – 33.7 °C** |

⚠️ **这是【电池】温度,不是 SoC 温度** —— 两者不是一个量级：
[任务 AN](plans/AN-TNT桌面模式性能优化.md) 测得的 SoC 是 **58–62 °C**（走 `/sys/class/thermal`）。
**不要把这两个数放在一起比较。**

#### ③ 代码里的三个边界（★ 都是踩过才知道的）

| # | 边界 | 处理 |
|---|---|---|
| **1** | ★★ **「真的 0 °C」与「没读到」必须分开** | `Reading.Ok.tempC` 是 **`Double?`** —— 解析不出给 **`null`**,**不是 `0.0`**。<br/>⚠️ 旧版给 `0.0`，卡片侧又判 `> 0.0` 才显示 ⇒ **两件事被混成一个** |
| **2** | ★ **正则要接受负数** | `(-?\d+)` —— 旧版 `(\d+)` **匹配不上负值**。实测全为正，<br/>但**语义上不该假设**（低温环境 / 传感器异常都可能为负） |
| **3** | ★ **只在确实解析出数字时才显示** | 正常显示 `33.6°C`；`null` 时该位置留空，**不显示 `0.0°C`** |

⚠️ **一处已知限制（未改）**：正则只认 `+BATCG=` 前缀。
AT 层里 `AT+BAT` / `AT+BATT` 回的是 `+BAT=` / `+BATT=`（**字段结构相同**，
见 [`_serial_probe.txt`](../refs/ccop_bridge/_serial_probe.txt) L28/L32）。
本 mod 只发 `at+batcg`，且设备的周期性推送也是 `+BATCG` ⇒ **当前不受影响**；
但若哪天改用别名命令，**解析会静默失败**。

#### ④ ★ `+HRM` 第 3 字段：新观测指向「计数器」而非 ADC

同批 15 组样本抓到一个此前没有的现象：

```
18:22:59  +HRM=0,335,1255
18:23:29  +HRM=0,335,1257     ← +2
18:23:59  +HRM=0,336,1259     ← +2
   ⋮          （连续 14 次，每次恰好 +2）
18:29:59  +HRM=0,337,1283     ← +2
```

**连续 14 次增量、每次恰好 `+2`、跨 7 分钟** ——
★★ **一个静态物理量的 ADC 不可能这样。**

⇒ **观测结论（只到这一步）**：该字段在**持续线性递增**，
**性质是「计数器」而不是「ADC 采样值」** ——
这与 [06 §6.2](06-TNTGO-AT命令全集.md) 把它记为「某路未知 ADC」**不一致**，该处已同步加注。

⚠️ **仍未确定**：它是「按**时间**递增」还是「按**读取次数**递增」——
本批样本轮询间隔恰好固定 30 s，**两种情况无法区分**。
★ **零风险判别实验**：相隔 ~2 s 连发两次 `AT+CHECK`。
- 仍 `+2` ⇒ 按**命令次数**
- 数值不变 ⇒ 按**时间**

（**未做** —— 串口被产品 mod 占着，见 [任务 AS](plans/AS-TNTGO状态栏扩展.md)。）

### 7.5 ★★★★ 容量自学习（2026-09-15,任务 AQ）

> **回写自**：[计划书 AQ](plans/AQ-TNTGO电量功耗与可用时间.md) AQ4（AQ10 收尾）
> **详档**：[任务 AR · 审计整改](plans/AR-审计整改.md) §0.2 / §10
> **代码**：[`TntgoCapacity.kt`](../projects/mode-launcher/src/mod-tntgo-battery/src/main/java/com/shware/mode/mod/tntgo/TntgoCapacity.kt)

#### ① ★★★★ 结论：**先验 10160 mAh 偏高,实测中位数 7137 mAh**

| | 值 | 来源 |
|---|---|---|
| **先验**（代码默认值 `PRIOR_MAH`） | **10160 mAh** | ★ **网络标称**（baike / mydrivers），**非实测** |
| **实测（3 段中位数）** | ★★ **7137 mAh** | 本机库仑计数自学习 |
| **三个独立样本** | **6270 / 7137 / 8630** | **全部低于先验** |
| 相对差 | **−29.8%** | 中位数 vs 先验 |

★★ **三段样本没有一个接近 10160** ⇒
「标称 10160」作为**可用时间的输入**是**不能用的**（用一个偏高的容量算可用时间**必然偏长**）。

#### ② 原理（一句话）

```
段 = 从某个整数电量百分比起,累计 ∫|I|dt
结段条件：ΔSOC ≥ 5%  且  有效时长 ≥ 10 分钟
C_est = 该段搬走的电荷 mAh ÷ ΔSOC
多段取【中位数】⇒ 得到容量
可用时间 = C × SOC% ÷ |I| × 0.90        ← 0.90 是用户指定的保守系数
```

★ **为什么用中位数**：单段噪声极大（实测三段最大相差 **38%**）⇒ 均值会被离群值拖走。

#### ③ ★★ 偏差方向纪律：**宁可少报,绝不虚报**

用户明确要求**偏向保守**（可用时间宁可短）。这条纪律**直接决定了算子怎么写**：

| 断档期间的电荷怎么处理 | `C_est` 方向 | 可用时间 | 判定 |
|---|---|---|---|
| **估算**回分子（更"准"） | **偏高** | 偏长 | ❌ **危险,不做** |
| **只扣时间、不补电荷** | **偏低** | 偏短 | ✅ **保守,采用** |

⇒ ★★ **"更准"和"更保守"是两个方向** —— 这里**故意选了偏保守的那个**。
★ 代码注释里留了**反例警戒**：将来若有人为了"修准"而把 gap 电荷补回分子，
偏差方向立刻翻转为**危险方向**。

#### ④ 算子层面踩过的三个坑（都已修,详档见 AR）

| # | 缺陷 | 偏差方向 | 触发频率 |
|---|---|---|---|
| **1** | ★★ **满电平台期** —— 段起点 = 100% 时，电量**钉在 100% 不动而电荷照涨**<br/>⇒ 分子白涨、分母不动 | **偏高** | ★★★ **每次从满电放电都触发** |
| **2** | **断档后把间隙电荷按当前电流编造进分子** | **偏高** | 偶发（读失败连成片） |
| **3** | **`MIN_SEG_MS` 摧毁已合格的段** —— 该判据排在 ΔSOC 检查**之后**，<br/>走到它说明段已合格，却整段丢掉 | —（**学不出来**） | ★ 真实容量越低 / 负载越重**越容易**触发 |

★ **坑 1 的实机证据**：修复前第一次学习产出 **11956 mAh（偏高 18%）**。
监看日志一眼看出机理 —— 前 ~90 mAh 是在电量钉在 100% 时积累的。
**反推验证**：`(598 − 约90) / 0.05 ≈ 10160`。

#### ⑤ ★ 一条重要的自洽性：**容量估计不受亮度影响**

用户裁定：「不同的亮度对应 tntgo 的功耗并不相同」——
⇒ **功耗读数与可用时间都受亮度影响**，但 **容量自学习不受**：

> 库仑计数积的是**实际电流** `∫I dt`。亮度变化只改变 `I`；
> 而 `+BATCG` 是**电池侧总电流**，背光耗电**已经含在里面**
> ⇒ `∫I dt ÷ ΔSOC` 仍然**无偏**。

⚠️ **但可用时间的【绝对值】受亮度影响** —— 这属于 [任务 AR](plans/AR-审计整改.md) §0.0 的
诚实性缺口（由 **AR12 功耗-亮度曲线**处理）。

#### ⑥ 怎么自己看 / 复现

```bash
# ① 盘上状态 ★ String 型存的是【元素文本】,不是 value= 属性
adb shell run-as com.shware.mode cat /data/data/com.shware.mode/shared_prefs/tntgo_battery.xml
#   <string name="cap.samples">7137.005,8630.246,6270.2593</string>
#   <float  name="cap.seg.mah" value="221.11" />     ← 进行中的段

# ② 事件流
adb logcat -s 'ModeMod/Tntgo' | grep -a '容量\|学到一个\|断档\|平台'
```

关键日志字样：

| 字样 | 含义 |
|---|---|
| `★ 学到一个容量估计：NNNN mAh` | 一段结出来了 |
| `容量更新为 NNNN mAh（已学习 N 段）` | 融合后的当前值 |
| `★ 满电平台：丢掉起步阶段` | 平台期修剪生效（坑 1 的修复） |
| `采样断档 Ns ⇒ ★段继续，断档单独记账` | 断档不再作废整段（坑 2 的修复） |
| `段有效时长不足 Ns（总 Ns − 断档 Ns < 10 分）` | 在**等**，不是在丢（坑 3 的修复） |

⚠️ **两处仍在评估**（不擅自改产品行为）：
① `MIN_SEGMENTS = 2` 是否过早（2 点时"中位数"退化成均值，**抗离群能力为零**）；
② 段间离散度是否要加门槛。详见 [AR §10.9](plans/AR-审计整改.md)。

⚠️ **一处诚实保留**：§③ 的保守性会让学习值**偏低**，
所以**真实物理容量应略高于 7137** —— 但即便如此**离 10160 仍差很远**，
⇒ **「先验偏高」这个结论不受影响**。

### 第二条通道:CDC-ACM AT 控制台
- ~~指令 `at+adb\r\n`~~ ⚠️ **该指令记载有误,见下方勘误**
- 回读 `+BATCG=3855,60,2,-929,275,2` → **第 2 字段 = 电量 %**
- 正则 `\+BATCG=\d+,(\d+),`
- 波特率:**115200**(两个开源项目默认)vs **9600**(qiedd ADB 教程)—— **两说并存,需实测**
- 社区已有两个只依赖 AT 串口的开源电量工具(见 §9)

> #### ⚠️ 勘误(2026-09-11 任务 I):`at+adb` **不是**电量查询命令
>
> 真机实测(`.ref/probe_raw/tntgo_serial_probe.txt` L13–18):**`at+adb` 的响应是
> `ADB ENABLE` + 裸 `OK`** —— 按 §7.2 的判据,**它是「设置型」**(开 ADB 通道),**不是查询**。
>
> **⇒ 正确的电量命令是 `at+batcg`**(回 `+BATCG=…`)。
> 社区工具之所以「用 `at+adb` 也能读到电量」,是因为 **`+BATCG` 本来就是周期性自动推送的** ——
> 任务 G 的**被动监听阶段(12 秒不发任何命令)照样收到了 `+BATCG=4235,100,2,…`**(同文件 L8)。
> 即:**它们读到的是推送,不是 `at+adb` 的回包。**
>
> ⚠️ **副作用提醒**:`AT+ADB` 会**改变设备状态**(开 ADB)。它不是断开链路的类型,
> 但**属于设置型 —— 不要放进批量探测表**。

## 8. 接入时序(真机 4.2 秒)

```
T+0.00s  typec: Sink(powered) connected
T+0.60s  USB host(xhci) 上线 / PD 协商 + dfp_send_uvdm
T+1.50s  typec 重协商 medium→high
T+3.40s  DP HPD 拉高
T+3.57s  DP 链路协商完成 2160x1440@60 4Ln
T+3.66s  DP ready
T+3.80s  USB 枚举:TNT Go (0x31CE:0x5101)
T+4.00s  HID 输入设备注册(hidraw0-2)
T+4.2s   TntManagerService: onUsbDeviceAttached → connectTntScreen()
```

> **关键**:DP 画面链路**先于** USB 枚举就绪。接上后需保持 **5–10 秒**才能走完协商。
