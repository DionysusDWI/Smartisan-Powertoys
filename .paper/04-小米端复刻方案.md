## 0. ⚠️ 对旧方案的三条硬错误纠正

交接包 `02_技术方案/小米17PM窗口管理器_技术方案_v1.md` 的 L1 命令清单**是在坚果 Pro 3(Android 10)上验证的**,
**不能直接搬到 Android 16**。以下三条必须纠正:

| # | 旧方案 | **A16 实况** | 证据 |
|---|---|---|---|
| 1 | `am stack resize <stackId> <l,t,r,b>` | **`am stack resize` 在 Android 11 起已被删除。** A16 的 `am stack` 只剩 `move-task / list / info / remove`。正确命令是 **`am task resize <taskId> <left> <top> <right> <bottom>`**(4 个**独立整数**参数) | `services/core/java/com/android/server/am/ActivityManagerShellCommand.java` `runStack()` / `runTaskResize()` |
| 2 | `settings put global development_enable_freeform_windows_support 1` | **键名写错了。** 常量 `DEVELOPMENT_ENABLE_FREEFORM_WINDOWS_SUPPORT` 的**值**是 **`"enable_freeform_support"`**。旧写法等于写了个不存在的键 | `core/java/providers/settings/Settings.java:13994` |
| 3 | `input --ext-display <...>` | **AOSP 9–16 全分支无此参数。** 正确签名:**`input [<source>] [-d DISPLAY_ID] <command> ...`** | `services/core/java/com/android/server/input/InputShellCommand.java:321` |

### ★ 第 4 条(本次新发现,最致命)

> **`am task resize` 只对已经处于 FREEFORM / MULTI_WINDOW 的任务生效。**
> 对全屏任务调用会 **静默失败**(`Slog.w("resizeTask not allowed on task=")` 后直接返回)。

```java
// WindowConfiguration.canResizeTask()  (WindowConfiguration.java:788)
mWindowingMode == WINDOWING_MODE_FREEFORM(5) || WINDOWING_MODE_MULTI_WINDOW(6)
// ActivityTaskManagerService.resizeTask()  (ActivityTaskManagerService.java:2951) 先查这一条
```

**⇒ 旧方案「连 `resizeMode=0` 的 App 也能改」的结论是错的** —— 能否改卡在**窗口模式**,不在 `resizeMode`。

**让任务进入 freeform 的可用手段**:
- `am start --display <id> --windowingMode 5`(`ActivityManagerShellCommand.java:666,822-826`)
- 或副屏被 `force_desktop_mode_on_external_displays` 置为 freeform 默认后,新任务天然落 freeform 栈
- 或走 AOSP 桌面模式

## 2. Freeform 在 Android 16 / HyperOS 上的真实状态

### 2.1 开关与代码链路(A16 源码核实)

```
settings put global enable_freeform_support 1
  → WMS.SettingsObserver 监听该 Uri(WindowManagerService 的 mFreeformWindowUri)
  → 回调 updateFreeformWindowManagement()
  → 更新 mAtmService.mSupportsFreeformWindowManagement
```

`ActivityTaskManagerService.java:909`:
```java
mSupportsFreeformWindowManagement =
    pm.hasSystemFeature(FEATURE_FREEFORM_WINDOW_MANAGEMENT)
    || Settings.Global.getInt(resolver, DEVELOPMENT_ENABLE_FREEFORM_WINDOWS_SUPPORT, 0) != 0;
```

`DisplayWindowSettings.getWindowingModeLocked()`:
```
mSupportsFreeformWindowManagement && (mIsPc || dc.isPublicSecondaryDisplayWithDesktopModeForceEnabled())
    → 返回 FREEFORM
```

**`DisplayContent.isPublicSecondaryDisplayWithDesktopModeForceEnabled()`**(`DisplayContent.java:5707`):
`mForceDesktopModeOnExternalDisplays && !isDefaultDisplay && !isPrivate() && 默认 device id`

> **关键连带效果**:同一条件下 `DisplayContent.getImePolicy()`(4313 行)返回 **`DISPLAY_IME_POLICY_LOCAL`**
> —— **输入法会跟着到外接屏**。这正是 TNT 体验里「副屏可打字」的关键开关。

### 2.2 ★ 推荐启用序列(全走 shell 身份)

```bash
settings put global enable_freeform_support 1
settings put global force_resizable_activities 1
settings put global force_desktop_mode_on_external_displays 1    # 强烈建议:副屏默认自由窗口 + 副屏本地 IME
settings put global enable_non_resizable_multi_window 1         # 可选:非 resizeable 应用也可多窗口
```

### 2.3 `resizeMode=0` 的真相

`Task.isResizeable()`(`Task.java:2884-2890`)=
`mForceResizableActivities && ACTIVITY_TYPE_STANDARD` || `ActivityInfo.isResizeableMode(mResizeMode)` || PiP

**⇒ 打开 `force_resizable_activities` 后,标准 Activity 全部变为可 resize。**

### 2.4 HyperOS 特有行为

| 类型 | 内容 |
|---|---|
| **有证据** | 小米官方文档《全局自由窗口适配说明》:「**MIUI 的小窗是基于 Android 的多窗口 Freeform 方案实现的**」,接口用标准 `android:resizeableActivity` / `onMultiWindowModeChanged` / `mWindowingMode=freeform` / `mBounds`(`dev.mi.com/xiaomihyperos/documentation/detail?pId=1593`) |
| **有证据(负面)** | Taskbar issue #301(升级 HyperOS 后浮窗不能缩放/拖拽)、#317(MIUI 上表现为分屏而非浮窗);HyperCeiler 注明「小窗-记住状态与位置」在 **Android 16 上尚不可用** |
| **有证据(框架层)** | 小米存在自有策略类 **`com.android.server.wm.MiuiFreeFormStackDisplayStrategy#getMaxMiuiFreeFormStackCount`**(LSPosed 模块 MaxFreeForm/FreeformUnlock 直接改它)→ **并发小窗数量与白名单由厂商策略裁决** |
| **未确认** | ~~`am task resize` / `am start --windowingMode 5` 是否被 HyperOS 拦截;`enable_freeform_support` 是否会被写回/重置~~ |

> **判定**:AOSP 链路 ✅ 完整存在且源码可证;**HyperOS 实际放行程度 ⚠️ 本项目第一号未知数**。

### 2.5 ★★★★★ 小米真机实测（2026-09-11，**第一号未知数已解**）

> 设备：小米 17 Pro Max（`2509FPN0BC` / `popsicle` / **Android 16 / SDK 36 / HyperOS OS3.0**）
> 外接屏：TNT GO → `Display 2 "HDMI 屏幕"`，2160×1440，`type EXTERNAL`，`FLAG_PRESENTATION`
> **全部只靠 `adb shell`（uid 2000），未 root、未用 Shizuku**

#### ✅ 结论：**核心能力跑通**

```
am start --display 2 --windowingMode 6 -n com.android.settings/.MainSettings
  → Task=3844  mode=MULTI-WINDOW
am task resize 3844 200 150 1380 1100   → bounds=[200,150][1380,1100]   ✅
am task resize 3844  60  60  900  700   → bounds=[60,60][900,700]       ✅
```
**视觉确认**：TNT GO 上出现**独立桌面（非镜像）+ 一个可缩放的浮动窗口**。

#### ★★★ 修正后的 recipe（`--windowingMode **5**` = FREEFORM）

| 步骤 | 命令 | 关键点 |
|---|---|---|
| ① 送到副屏**并进入自由窗口** | `am start --display <ID> --windowingMode **5** <component>` | **用 5（FREEFORM）= MIUI 小窗** |
| ② 改窗口几何 | `am task resize <TASK_ID> <left> <top> <right> <bottom>` | 4 个**独立整数**;任务须已在 FREEFORM/MULTI_WINDOW |

**⚠️ `5` 与 `6` 都能让任务脱离 fullscreen,但语义完全不同**:

| | `5` = **FREEFORM** | `6` = MULTI-WINDOW |
|---|---|---|
| HyperOS 视作 | ✅ **MIUI 小窗** | ⚠️ **「分屏」** |
| 系统 chrome | ✅ **自带 ⤡ 拖拽/缩放手柄** | ❌ **无任何装饰** |
| 附加提示 | 无 | ⚠️ 部分 App 弹 **「当前页面不支持分屏,请切换至全屏使用」** |
| `am task resize` | ✅ 生效 | ✅ 生效 |

**⇒ 结论:用 `5`。** 它天然带拖拽手柄,且不会被当成分屏。

> **⚠️ 一条需要存疑的记录**:本次早期(显示器重连**前**)用 `5` 启动的任务落成了 `fullscreen`;
> 重连 + `force_resizable_activities=1` **之后**,`5` 正常产生 FREEFORM。
> **尚不能确定是哪个变动起的作用** —— 但在当前设备状态下 `5` 可用。

#### 失败路径的完整因果（全部实测）

### 2.8 ★★★★ 上滑手势失效 —— 根因坐实(2026-09-11 实测)

#### 现象

全面屏手势下,**「上拉悬停进多任务」**与**「上拉回主屏」**无法稳定触发,

#### ★ 根因:**`GestureStubHome` 的 `touchableRegion` 被裁**

而是由 launcher(`com.miui.home`)注册三个**手势桩窗口**承载:

| 窗口 | 职责 | touchableRegion(正常) |
|---|---|---|
| `GestureStubLeft` | 左侧返回 | `[0,288][62,2534]` |
| `GestureStubRight` | 右侧返回 | `[1138,288][1200,2534]` |
| **`GestureStubHome`** | **上滑回主屏 / 悬停进多任务** | **`[0,2533][1200,2608]` ← 必须全宽** |

#### ★★ 同机对照组(决定性证据)

**同一台小米 17 Pro Max、同一 build、同一导航模式(=2),唯一差异:**

| | 故障态(16:50) | 正常态(17:0x) |
|---|---|---|
| `GestureStubHome` frame | `[0,2534][1200,2608]` | `[0,2533][1200,2608]` |
| **`GestureStubHome` touchableRegion** | **`[652,2534][1200,2608]`** ❌ **只有右半** | **`[0,2533][1200,2608]`** ✅ **全宽** |
| `GestureStubLeft` | `[0,288][62,2534]` | `[0,288][62,2534]` ← 一样 |

### 2.10 ★★★★★ MIUI 自由窗口的【内容缩放 = 0.7】—— **会决定整个自研 WM 的几何换算**(2026-09-11 实测)

> **来源**:任务 N · **纯实测**(逐像素量截图,非推断) ｜ 工具:[`tools/measure_freeform.py`](../archive/xiaomi-tnt-wm/tools/measure_freeform.py)

**`am task resize` 改的是【容器】,不是用户看到的画面。** 两者差 **0.7 倍**:

| 请求容器 | 窗口 `frame` | **可见内容** | **内容 ÷ 容器** |
|---|---|---|---|
| 2160×1440 | 2160×1440 | 1512×1008 | **0.7000** |
| 1080×1440 | 1080×1440 | 756×1008 | **0.7000** |
| 1600×1000 | 1600×1000 | 1120×700 | **0.7000** |
| 820×680 | 820×680 | 574×476 | **0.7000** |

**⇒ 内容 = 容器 × `0.7`,锚定容器左上角(偏移恒为 +0,+0)。**

#### ★ 补偿成立 —— 自研 WM 的路走得通

```
请求容器 0 0 3086 2057   (= 2160/0.7 × 1440/0.7)
  → frame = [0,0][3086,2057]                ← ★ 容器【可以超出显示屏】,不被钳位
  → 内容  = 2160×1440                        ★ 精确铺满整屏 ✅
请求容器 0 0 1543 2057   (= 1080/0.7 × 1440/0.7)
  → 内容  = 1080×1440                        ★ 精确铺满左半屏 ✅
```

**⇒ 要内容铺满 R,请求容器 = R ÷ 0.7。**

#### ⚠️ 还有一个【用户缩放因子】`mFreeformScale`

小窗**可双指缩放**,该缩放记录在 `mFreeformScale`,**与 0.7 相乘**:

```
mFreeformScale=1.0        → 内容 = 容器 × 0.7
mFreeformScale=0.1388889  → 内容 = 容器 × 0.7 × 0.198 ≈ 容器 × 0.1389
```

⚠️ **这就是「`am task resize` 明明成功、几何也对,画面却只有一小块」的真凶。**
复位办法:**杀掉该 App 重新启动**(实测有效)。
⇒ 代码**刻意不补偿它**(补偿需请求 7 倍大的容器),改为**明确告警**。

#### 对项目的三条含义

1. **「回读 bounds 验下游」不足以证明用户看得到** —— 需要量画面时,用
   [`measure_freeform.py`](../archive/xiaomi-tnt-wm/tools/measure_freeform.py) 逐像素量。
2. **自研 WM 的所有几何换算必须带 `/0.7`** —— 否则窗口只有目标的 70% 大。
3. ⚠️ **这是 MIUI 特有行为,AOSP 没有。换机 / 换系统版本【必须重测】**(已写进代码注释)。

## 3. 非默认显示器上渲染 UI 的手段对比

**两条底层事实**:
- HDMI/DP 外接屏由 `LocalDisplayAdapter` 注册,flags = **`FLAG_PRESENTATION + FLAG_TRUSTED`,默认不带 `FLAG_PRIVATE`**(`LocalDisplayAdapter.java:826-838`)
- 门禁 `Display.hasAccess()`(`Display.java:2102`):**非 private 屏对任何 uid 放行**

| 手段 | 能否承载第三方 App 窗口 | 权限 | A16 判定 |
|---|---|---|---|
| **A1 `Presentation`** | ❌(是 Dialog,只能画自己内容) | 无 | ✅ 可用;A16 新增 `PresentationController`,flag 开启时会**遮蔽该屏全部 Activity**,且全局仅允许一个 → **只适合自有内容面板,不做桌面壳主体** |
| **A2 `createDisplayContext(display)` + `createWindowContext(TYPE_APPLICATION_OVERLAY)`** | ❌(只能"覆盖"不能"包含") | App 身份要 `SYSTEM_ALERT_WINDOW`;**shell 身份持 `SYSTEM_APPLICATION_OVERLAY`,连 appops 都不查** | ✅ **官方姿势**(`Context.java:7760-7790`)→ **本项目在副屏画桌面/Dock/标题栏的核心手段** |
| **A3 `ActivityOptions.setLaunchDisplayId()`** | 部分(决定落屏,不改形态) | 公开 API;shell 因持 `INTERNAL_SYSTEM_WINDOW` 直接放行 | ✅ **不限于自己的 App** → "点图标 → 开到副屏"的正解 |
| **A4 `VirtualDisplay` + `MediaProjection`** | ❌ | A14+ 每次要用户同意 + 强制 FGS;VD 默认 private;shell 无 `MANAGE_MEDIA_PROJECTION` | ⚠️ **不建议**(物理屏已存在,绕 VD 无收益) |
| **A5 系统桌面模式(WMShell)** | ✅(装饰属于系统) | 厂商 config | ⚠️ AOSP 有全套(`DesktopModeWindowDecorViewModel`),但 `config_isDesktopModeSupported` **默认 false**;`ENABLE_PROJECTED_DISPLAY_DESKTOP_MODE` 的 dev-option 覆盖参数为 **false** → **小米是否开放未确认** |

### ★「跨 App 窗口装饰」的最终答案:**公开 API 做不到**

现实三条路(按可行性):
1. **系统桌面模式可用** → 标题栏/拖动/resize 由 WMShell 提供,壳只做桌面与任务栏
2. **shell uid + 隐藏 API** → `WindowOrganizer/TaskOrganizer` 操作第三方 task surface,或 **`WindowInfosListener`** 拿全系统窗口几何(javadoc 原文 "should only be done within **system_server and shell**",需 `ACCESS_SURFACE_FLINGER`,**shell 恰好持有**),再自绘 overlay 装饰 —— **这是无系统桌面模式时的现实主路线**
3. 纯 overlay 伪装饰(固定位置画边框)—— 体验差,仅降级用

### ★★ 对照:TNT 自己是怎么做的(2026-09-10 任务 C 新增)

TNT 用的是**比上面三条都更底层**的第四种手段 —— **直接搬 SurfaceControl**:

| 能力 | TNT 的实现 | 小米(无 root / A16)能否照搬 |
|---|---|---|
| 把**别的 App 的 task** 嵌进自家 View | `ActivityStackView`(宿主 View 拿到一条 SurfaceControl **leash**,系统把目标 stack 的 Surface `reparent` 进去)—— [02](02-TNT系统结构规格.md) §8.7 | ❌ **不能**。第三方拿不到别的 task 的 SurfaceControl;AOSP 近似物 `ActivityView` 要求目标 `allowEmbedded` + `EMBED_ACTIVITY` 权限 |
| 把 **TNT 上的 task 搬到手机屏**(活体,非截图) | `CrossDisplayController.reparentTaskStackSurfaceLocked` —— `TaskStack.SurfaceControl.reparent(CrossMirror_<taskId>)` + 客户端算矩阵回传做**输入反变换** —— [02](02-TNT系统结构规格.md) §8.8 | ❌ **不能**(同上,需 `system_server` 身份) |

> **意义**:这解释了为什么 TNT 能做到「应用互相内嵌」「跨屏拖活窗口」——
> **它改的是 `system_server` 里的 `WindowManagerService`/`ActivityTaskManagerService` 本身**。
> 小米端既然不能改系统,**必须放弃"复刻这两个能力"的念头**,
> 改为把 §3 表的 **A2(shell 身份 overlay)+ A3(`setLaunchDisplayId`)** 做到极致。
> (若只求「形似」,可用**任务快照**做静态缩略图,但**不是活体**,体验差距明确。)

### ★ 顺带:TNT 的触摸/鼠标模式切换 —— **小米端不需要重建**(2026-09-11 更正)

TNT 的设计意图确实是**按 TNT GO 内置加速度计倾角**自动切模式(阈值 70°、滞回 `[65°,75°]`),
并据此**翻转标题栏位置**(鼠标→顶,触摸→底)—— 判定链见 [02](02-TNT系统结构规格.md) **§8.9**。

> #### ⚠️ 但这条**在有线场景下根本不激活** —— 本节初版结论(「只能用启发式近似」)已作废
>
> **用户告知(硬件事实)**:**加速度计是给 R2 的「无线连接」用的;
> 坚果 Pro 3 只能有线连接,因此用不到加速度计。**
>
> **代码三条印证**(详见 [02](02-TNT系统结构规格.md) §8.9.3 v1.7 勘误):
> 1. `tryOpenAccelSensor()` 有**显式放弃路径** —— `if (i >= 10) return;`(试 10 次后**永久停手**)
> 2. **手机自己有加速度计**(`dumpsys sensorservice` 实测 `icm4x6xx`),代码找的却是**「外接屏的」**
>    ⇒ 是另一条通道,与手机本体无关
> 3. 传感器找不到 ⇒ `mDecorCaptionOperatingModeBySensor` **恒为 `-1`**
>    ⇒ 消费端 `getCaptionTouchMode() != 1` ⇒ **固定落到「鼠标模式」**(标题栏在顶)
>
> #### ★★ 对小米端的推论
>
> **小米 17 Pro Max 同样是「有线」接 TNT GO ⇒ 传感器同样找不到 ⇒ 行为是确定的。**
>
> **⇒ 不需要启发式近似,直接按固定行为实现:「鼠标模式 / 标题栏在顶」。**
> 这与真机(坚果 Pro 3)的表现一致,且**与 TNT GO 的型号无关** —— 只要是有线。
>
> **⇒ 同时从待办中移除**:「TNT GO 加速度计的传输通道」不再需要追查
> (它属于无线版 + R2 的场景,不在本项目范围内)。

## 4. 窗口几何获取与控制

**获取**:
- **Binder(推荐)**:`IActivityTaskManager.getAllRootTaskInfosOnDisplay(displayId)`、`getTasks(...)`、`registerTaskStackListener(ITaskStackListener)`
  - shell 持 `MANAGE_ACTIVITY_TASKS`,可直接调用
  - ⚠️ **`TaskInfo.bounds` 在 Android 17 已移除**(改读 `windowConfiguration`)→ **现在就应读 `windowConfiguration`**
- 命令(兜底):`dumpsys window displays`、`dumpsys activity activities`

**控制**:
- `am task resize <taskId> <left> <top> <right> <bottom>` —— **前置条件:任务已在 FREEFORM/MULTI_WINDOW**
- `am display move-stack <rootTaskId> <displayId>` —— 把整个 root task 搬到副屏
- `wm size -d <displayId>` / `wm density -d <displayId>` —— A16 支持 `-d`
  - ⚠️ **改副屏密度会让已有窗口 bounds/吸附像素口径全变**(1207px 半屏、4px 边距都是按 2160×1440 推的)

## 5. 输入注入与隔离

- 正确签名:**`input [<source>] [-d DISPLAY_ID] <command> [<arg>...]`**
- 命令集:`text / keyevent / tap / swipe / draganddrop / press / roll / scroll / motionevent / keycombination`
- **`-d` 默认值**:按键事件 −1(跟随焦点),运动事件 0(默认屏)→ **要打到副屏必须显式 `-d <extDisplayId>`**
- **多点触控 CLI 不支持** → 需走 binder `IInputManager.injectInputEvent(MotionEvent, mode)`(shell 持 `INJECT_EVENTS`),自构造多 pointer MotionEvent
- ⚠️ **延迟**:`input` 每次都要起 `app_process` JVM,**百毫秒级**,做窗口拖拽会明显掉帧
  → **拖拽/缩放必须走常驻 UserService 里的 binder 注入**

## 6. 通知面板

- 自研 `NotificationListenerService` + 自绘面板即可;`getActiveNotifications()` 默认拿完整 `StatusBarNotification`
- 「通知使用权」是**特殊访问权限**,与 `POST_NOTIFICATIONS` 无关
- 脱敏只发生在带敏感标记且 listener 未受信任时(信任 = `RECEIVE_SENSITIVE_NOTIFICATIONS`);**判定看 listener 服务的 uid** → 普通 App 身份的 NLS 会被脱敏
- 渲染到副屏:用 §3.A2 的 overlay 自绘(建议自绘,不用 RemoteViews)
- 点通知 → 开到副屏:`ActivityOptions.setLaunchDisplayId` + launcher intent(推荐)
- **⚠️ HyperOS 风险**:MIUI/HyperOS 会因「非应用商店签名」拒绝给侧载应用授予**通知使用权/无障碍**
  - 解法:应用信息 → 右上角 → 「允许受限权限」,或 `cmd notification allow_listener <pkg>/<svc>`

## 7. 把应用启动到指定显示器

- `am start --display <displayId> [--windowingMode 5]` —— A16 可用
- **不限于自己的 App**:`ActivityTaskSupervisor.isCallerAllowedToLaunchOnDisplay()`(1242 行)中,持 `INTERNAL_SYSTEM_WINDOW` 的调用方**直接放行**;非 private 公共屏对普通调用方也放行 → **shell 身份两者都占**
- App 侧(普通 uid)用 `ActivityOptions.setLaunchDisplayId` **只能启动自己的 Activity**
- **⇒「任何第三方 App 到副屏」的可靠手段是 shell 身份的 `am start --display`**
- ⚠️ **`am start` 没有 `--bounds` 选项** → 落屏后要用 `am task resize`(前提见 §0.4)
- AOSP 自带的"三步放置等价物":`DesktopModeBoundsCalculator`(`persist.wm.debug.desktop_mode_initial_bounds_scale` 默认 75%、`DESKTOP_MODE_LANDSCAPE_APP_PADDING=25`、`WINDOW_HEIGHT_PROPORTION=0.375`)

### 9.2 另一条关键命令(本方案此前遗漏)

```bash
am task resizeable <TASK_ID> [0|1|2|3]
#   0 = unresizeable
#   2 = resizeable
#   3 = resizeable_and_pipable
```

### 9.3 TNT 的真实结构(它的逆向结论)

```
底层外接屏(base display,须过 SmtPCUtilsInner.isValidExtDisplayType())

  → 该虚拟显示被重映射到 100000+

```

> **复刻不必照搬这套 display 分层**,但理解它可以解释「为什么 TNT 桌面能固定跑在一个虚拟屏上再镜像出去」。

5. **HyperOS 是否开放桌面模式**:开发者选项里找 "Enable desktop experience features";`getprop persist.wm.debug.desktop_experience_devopts`
6. **`input -d <extId>` 是否真打到副屏**;物理鼠标/键盘插到手机后事件落在哪块屏(**决定"输入跟随"实现**)
7. **overlay 在副屏的 z-order**:与 freeform 窗口、状态栏、IME 的层叠关系
8. **NLS / 无障碍的受限权限**:侧载后能否授予;不能则验证 `cmd notification allow_listener`
9. **拔插显示器**:task 是否重定位、overlay 是否移除、重插后 displayId 是否变化
10. **`wm size/density -d <extId>`** 是否生效,及改动后 `am task resize` 的坐标口径变化

> ★ 公开镜像说明：本文中的局域网地址已掩码为 `<设备IP>`。结论与判据未作任何改动。
