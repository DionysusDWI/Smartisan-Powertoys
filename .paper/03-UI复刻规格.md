## 0. 首要结论:哪些能抄、哪些不能抄

| 组件 | 实现方式 | 复刻策略 |
|---|---|---|
| **TNT 桌面本体**(壁纸 + 图标网格) | **OpenGL 自绘**(`com.smartisanos.launcher.view.SMGLSurfaceView`) | ❌ **无布局可抄** —— `large_screen.xml` 仅 7 行(一个 GLSurfaceView + 一个重命名 EditText)。必须自行设计。 |
| **dock / 最近任务 / 通知面板 / 快捷开关** | 传统 XML 布局(SystemUI) | ✅ **可精确参考** —— 457 个布局已解码 |

> 这是复刻工作量的关键分野:**系统 UI 可照搬规格,桌面本体需原创设计**。

## 2.2 ★ TNT 快捷键完整映射(系统设置实证)

来源:`settings list global | grep custom_key`

> ⚠️⚠️ **勘误(2026-09-10 任务 D)** —— 本节原先写 **「格式:`<触摸模式>$<键盘/鼠标模式>`」,两个列名都错了**。
> **正确格式是 `<mac>$<win>`(Mac 键盘布局 / Windows 键盘布局)。**
>
> **铁证**:`SmtPcPhoneWindowManager.updateShortcutSettings` 的日志语句**直接命名了列**:
> ```java
> Log.d(TAG, "... mac mode key: " + shortcutInfo2.shortcuts[0].keycode + " ..."
>            + "win mode key: " + shortcutInfo2.shortcuts[1].keycode + " ...");
> ```
> 且选择逻辑是**逐事件的标志位**,与系统模式无关(同文件 L1183-1190):
> ```java
> boolean isMacMode = (event.getFlags() & 2048) != 0;   // 2048 = KeyEvent.FLAG_MAC_MODE(Smartisan 自加)
> if (isMacMode) shortcut = shortcutInfo.shortcuts[0];  // mac
> else           shortcut = shortcutInfo.shortcuts[1];  // win
> ```
> **⇒ 触摸/鼠标模式与快捷键列选择是两套完全独立的机制**(触摸/鼠标见 [02](02-TNT系统结构规格.md) §8.9)。
>
> **⚠️ 下表的「数据」是正确的**(直接来自设备设置),**只有两个列名需要按 `<mac>$<win>` 重读**。

---

### ★★★ 实测结案(2026-09-11,真机按键):**生效的是 `win` 列**

> **来源**:Operit(手机端)在 TNT GO 键盘上**真人按键**实测 ——
> 注入法测不了(见 §2.5②),真机按键才行。
> 证据:`TntPhoneWMImpl` 日志 `interceptKeyBeforeDispatching ... flags = 8 ... result = ...`

**三重印证:**

| # | 证据 | 结论 |
|---|---|---|
| 1 | **日志直接给出标志位**:`flags = 8` ⇒ `isMacMode = (8 & 2048) != 0` = **`false`** | **win 列** |
| 2 | **行为**:`Win+D` ✅ 生效(win 列绑定) / `Win+M` ❌ 无效(win 列 = `NONE`) | **win 列** |
| 3 | **`result` 语义**:`-1` = TNT 已命中执行 / `0` = 未命中(`handleByCustomShortcuts` 的 `default: return 0`) | 与上两条自洽 |

**⇒ `CC` 早前「`boston_keyboard` 带 `FLAG_MAC_MODE` ⇒ 走 mac 列」的推断被证伪。**
**真机 TNT GO 键盘按键 `flags=8`,不置 `FLAG_MAC_MODE`。**

#### ★★ 因此:**本机实际生效的快捷键 = 下表 `win` 列**

### ④ ★★ 7 个「死键」—— 复刻的关键发现

键盘上排有 **7 个专用键**,全部落成同一个键码:

| HID 扫描码 | HID 标准定义(Usage Page 0x07 System Control) | Linux 键码 |
|---|---|---|
| `0x000700a5` | System App Menu | **240 = `KEY_UNKNOWN`** |
| `0x000700a6` | System Menu Help | 240 |
| `0x000700a7` | System Menu Exit | 240 |
| `0x000700a8` | System Menu Select | 240 |
| `0x000700a9` | System Menu Right | 240 |
| `0x000700aa` | System Menu Left | 240 |
| `0x000700ab` | System Menu Up | 240 |

**根因**:
1. **TNT GO 没有专属 keylayout**(无 `Vendor_31ce_Product_5101.kl`)→ 只能用 `Generic.kl`
2. `Generic.kl` **未定义** HID usage `0xA5–0xAB` 的映射 → 内核统一归到 `KEY_UNKNOWN (240)`
3. **7 个键因此无法区分** —— 唯一区分依据是 **MSC_SCAN 的 HID usage**

**对复刻的意义**:
- **TNT GO 键盘的这 7 个键在 Android 上是「死键」**,除非自定义 keylayout 按 **scanCode** 映射
- 小米端自研 WM **可以主动利用这一点**:自行分配这 7 个键的功能
- **对照组**:同一键盘的 `0x46`(PrintScreen)→ `KEY_SYSRQ(99)`、`0x4C`(Delete Forward)→ `KEY_DELETE(111)` —— **映射正常的键说明键盘本身工作正常,问题只在缺映射**

> 复刻 TNT GO 等价外设时,**这 7 个 usage 应保持原样**(否则会与真机行为不一致);
> 而**适配 TNT GO 到小米端**时,应补一个 keylayout 把这 7 个键激活。

### ⑤ 复刻启示

| 发现 | 小米端对策 |
|---|---|
| F1–F12 标准 | 直接沿用 Windows 习惯的绑定 |
| 音量/亮度走 Consumer Control | 系统自带处理,无需额外工作 |
| **7 个专用键是死键** | **补 keylayout 按 scanCode 映射**,或自行分配功能 |
| Win 键齐备 | TNT 那套 `Win+*` 快捷键**可以照搬** |

> 1. `TntPhoneWMImpl.interceptKeyBeforeDispatching` **每次拦截都打日志**(含 `flags`/`result`),

>
> **⇒ 结论:TNT 快捷键无法用 adb 注入测试,只能用真机手按。**
> 正确方法见 [计划书 D](plans/D-已知模式重测TNT快捷键.md) §7。

> ✅ **2026-09-11 已结案**:由 **Operit 在 TNT GO 键盘上真人按键**完成判定 ——

### ④ ★★ `smtConfig` —— Smartisan 在 `Configuration` 里加的自定义字段

`dumpsys window windows` 可见,这是交接包**未记录**的一层:

    mAsvId=-1          mTypeExt=0        mRotationExt=-1
    mDensityDpi=0      mBoundsExt=Rect(0,0-0,0)
    mAppBoundsExt=Rect(0,0-0,0)          mParentBounds=Rect(0,0-0,0)

```

**推测用途**(字段名语义 + TNT 需求):

| 字段 | 推测含义 |
