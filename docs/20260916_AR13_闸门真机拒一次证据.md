## 4 · ★★★ 是不是「误杀」？—— 查过了，是**真阳性**

**我怀疑的第一件事**：档位里那两条**证据薄**的档（`mcu=94, n=1` ／ `mcu=178, n=2`）
会不会是**单点噪声把闸门骗响**？⇒ 去读了逐样本明细：

```
  MCU   44  n= 68  median= -969.0   min= -1251  max=  -872  spread= 379
  MCU   71  n= 27  median=-1001.0   min= -1097  max=  -898  spread= 199
  MCU   94  n=  1  median=-1109.0
  MCU  178  n=  2  median=-1612.0   min= -2108  max= -1116  spread= 992   ← ★ 992 mA
  MCU  497  n= 23  median=-1344.0   min= -1814  max= -1169  spread= 645
  MCU 2000  n=  8  median=-2068.0   min= -2171  max=  -405  spread=1766
```

**结论（实测，非推断）**：

1. ★ **真正把闸门打响的那一对是 `497 → 2000`**（`1344 → 2068`）——
   ★★ **两边都是证据充分的档**（`n=23` 与 `n=8`），**不是**单点噪声骗的。
   那条 `980.4 + 0.5745·MCU` 的直线是**被 `497` 这一档拽下来的**（它比 `44→94→178` 的趋势低）。
2. `mcu=178` 那一档 `n=2`、**档内离散 992 mA** —— 其中 `-1116` 与 `-2108` 明显来自
   **充/放状态切换的瞬态**（与 AR12b-2 抓到的「假达标」同族）。
   ⇒ 这条**不是**误杀的来源，但它**是**一个真实存在的**档位选取缺陷**（见 §6）。

⇒ ★★ **所以拒绝是正当的**：那条直线上挂着**至少一个异常档**，用它插值会给出**四位数毫安的假读数**。
AR13 的注释里写过这个后果，本次是它**第一次在真机上真的发生了**。

## 5 · ⚠️ 过程中的一个坑：`install -r` 之后电量 mod 不会自己回来

| 组件 | 装机后的命运 | 为什么 |
|---|---|---|
| `:mod_brightness` | ✅ **自动重生**（pid 6902） | 它是**无障碍服务**，由系统绑定 ⇒ 系统负责重新绑定 |
| `:mod_tntgobat` | ❌ **没有回来**，`dumpsys activity services` 里查无此服务 | 它是普通前台服务；`LauncherService.syncOnce()` 的**补拉**要等宿主走一次同步 |

★ **后果**：不拉起电量 mod，**`gate()` 根本不会被执行**，`曲线重算` 那行日志也不会出现
⇒ **「装完就去看日志」会看到一片安静，容易误判成「闸门没接线」**。
★ 本轮的解法：按 `ModRuntime.start()` 的原样手动投喂（`--ei displayId 100000`）——
等价于 `startForegroundService` ＋ 三个 extra，**没有改动任何产品代码**。

```bash
adb -s 192.168.1.10:5555 shell am start-foreground-service \
  -n com.shware.mode/com.shware.mode.mod.tntgo.TntgoBatteryService \
  -a com.shware.mode.action.MOD \
  --ei com.shware.mode.extra.DISPLAY_ID 100000 \
  --es com.shware.mode.extra.TARGET tnt \
  --es com.shware.mode.extra.LAUNCHER_PACKAGE com.shware.mode
```
