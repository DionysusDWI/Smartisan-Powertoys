## 1 · 前置突破：解决了「怎么截 TNT GO 副屏」

AR12d 长期卡住的**取证前提**是：`adb exec-out screencap` 只能拿到**手机屏**（1080×2340），
拿不到 TNT GO 上的悬浮卡片。本轮解决。

| 事实 | 值 | 来源 |
|---|---|---|
| 逻辑屏（TNT 桌面） | `displayId=100000`，`smt.tnt.virtual.display`，VIRTUAL | `dumpsys display` |
| **物理屏（截图要用这个）** | **`10652974438123012`**，`P120ZDG-BF4`，HWC display 1，port=4 | `dumpsys SurfaceFlinger --display-id` |
| 手机屏 | `19260388476191617`，`rm692a9 1080p`，HWC display 0 | 同上 |

★ **关键区分（本次踩到的概念坑）**：`dumpsys display` 里 `mOverrideDisplayInfo`
把 **displayId 100000 重定向到 HDMI(displayId 8)** ⇒ 「100000」这个数在**不同层含义不同**。
而 **`screencap -d` 只认 `dumpsys SurfaceFlinger --display-id` 输出的物理 ID**（该 ROM 的
`screencap -h` 明确写了这一点：`-d: specify the physical display ID to capture`）。

**可用命令**（已实测 exit 0）：

```bash
adb shell screencap -d 10652974438123012 -p /sdcard/ar12d_tnt.png
adb pull /sdcard/ar12d_tnt.png
```

产物 1366834 B / **2160×1440** —— 与副屏分辨率一致，卡片确实在画面内。

## 3 · 判据对账（**决定性**）

AR12d 原始判据（计划书 §14.6）：

> 卡片上那个数 **== 当场从 `bkl.curve` 算出来的曲线值**，**且 ≠ `+BATCG` 的瞬时电流**。

### 3.1 当场台账快照（`shared_prefs/tntgo_battery.xml`，`run-as` 读出）

```
bkl.curve = {"v":2,"legacy":110,
  "chg":"23:3704.0:1;497:3536.0:70;2000:2888.5:8",
  "dis":"71:1001.0:15;497:1344.0:23;2000:2068.0:8",
  "ts":1789485528749}
```

同一时刻 `files/tntgo_brightness.state` = `mcu=71, ui=30`（心跳新鲜）。

### 3.2 独立复算（**不使用 App 的曲线，只从原始样本重算**）

从 `bkl.samples` 的 125 条 4 字段样本（`ui:mcu:mA:flag`）重算：

| 组 | 档位（MCU → \|I\| 中位，n） | 拟合 |
|---|---|---|
| **放电** | `71 → 1001.0 (15)` ／ `497 → 1344.0 (23)` ／ `2000 → 2068.0 (8)` | `\|I\| = 1024.73 + 0.53809·MCU` |
| 充电 | `23 → 3704.0 (1)` ／ `497 → 3536.0 (70)` ／ `2000 → 2888.5 (8)` | `\|I\| = 3748.78 − 0.42945·MCU` |

★ **两组的档位与 App 盘上的 `bkl.curve` 逐项 MATCH**（MCU、中位、条数三者全等）。
⇒ **App 的曲线不是它自己记错的值**；下面这个对账因此可信。

### 3.3 卡片那个数

| 模型 | MCU 71 处的 `\|I\|` | `× 3.811 V` | 卡片应显示 |
|---|---|---|---|
| ★ **曲线值** | `1024.73 + 0.53809×71` = **1062.93 mA** | **4.0508 W** | **`4.1 W`** |
| 瞬时值（`+BATCG`） | 1001 mA | 3.8148 W | `3.8 W` |

**卡片实测显示 `4.1 W` ⇒ 与曲线值一致，与瞬时值不一致 ⇒ 判据成立。**

> ★★ **注意电压**：卡片用 `ok.millivolts = 3811`，**不是明细行的 3815**。
> 我一度用 3815 口算，得 4.083 W/3.815 W **两者都进位成 4.1 W**，险些得出
> 「本测试点无分辨力」的错误结论。**用对电压后分辨力是充分的（4.1 vs 3.8）。**

### 3.4 「曲线」这个后缀本身不可能来自别处（结构性论证）

`TntgoBatteryService.kt:635` 里 `（曲线）` 后缀是 `when` 表达式**唯一**产出 `InBand` 分支的返回值：

```kotlin
val where = when (est.where) {
    TntgoBklCurve.Where.InBand -> return "$base\n                @ $pct（曲线）"
    ...
}
```

而进入 `est` 非空分支还需 `bkl != null && !ok.charging`（`:574`）。
`estimate()` 给出 `InBand` 的条件是 `lo.mcu <= mcu <= hi.mcu`（`TntgoBklCurve.kt:240-243`），
而放电带 `lo.mcu = 71`、当前 `mcu = 71` ⇒ **恰好落在下边界 ⇒ InBand**。

## 4 · 途中排除的一个**假警报**（免得后人重踩）

现象：`dumpsys battery` 报 `AC powered: true`（充电中），而卡片同时显示 `↓放电` ＋ 走了曲线。
**看似自相矛盾。**

**真相**：两者是**两块不同的电池**。

| 读数 | 对象 | 含义 |
|---|---|---|
| `dumpsys battery AC powered=true` | **手机** | 手机插着充电器 —— 与副屏无关 |
| 卡片 `↓放电` / 曲线 | **TNT GO 副屏自己的电池** | `+BATCG` 帧的第 4 字段 |

且放电判据是**电流符号**，不是那个 status 字节：
`TntgoSerialReader.kt:114` `val charging get() = currentMa > 0`。
末帧 `+BATCG=3811,47,2,-1001,304,2` ⇒ `currentMa = -1001 < 0` ⇒ 放电 ⇒ 走曲线。
⇒ **无矛盾，卡片自洽。**（顺带纠正：`+BATCG` 第 3 字段 `2` 在本机对应**放电**，
与卡片 `↓放电` 一致；协议里它的确切语义仍未查，故**代码不依赖它**。）

## 4.2 第二处**自我纠正**：一个不存在的 bug

我一度怀疑 `renderPower()` 有**负瓦数** bug —— 因为 `learned` 做了符号处理
（`if (ok.currentMa < 0) -it else it`）而 **`liveMa` 没做**，若 `median()` 返回负值，
`watts()` 可能算出负功率。**核对后不成立**：`TntgoPower.kt:67` 的
`watts()` 里已有 `abs(currentMa)`，符号被吃掉。
⇒ ★ **降级路径不会出现负瓦数。**（本条记录在此，避免重复怀疑。）

## 5.2 ★★★ 附带发现：「反物理拒绝闸门」在产品运行时**从未接线**

验收过程中对代码做交叉复核时发现：`PROGRESS-STATE.MD` 与 AR12 计划书称 `gate()` 有**两道**闸门，
但**产品运行时只有一道**。

```kotlin
// TntgoBklCurve.kt:214-215 —— gate() 只做"档位够 + 拟合得出"
fun gate(levels: List<Level>): Gate =
    if (levels.size >= MIN_LEVELS && fitLine(levels) != null) Gate.Ok else Gate.NotEnoughLevels
```

`maxDrop()`（`:262-271`，注释自称"反物理 ⇒ 曲线不该被采用"）**全仓库零调用点**
（`grep maxDrop` ⇒ 仅其定义；`gate()` 就在它正上方 47 行却未连起来）。
⇒ **非单调（更亮却更省电）的曲线不会被拒绝**，会照常 `Gate.Ok` 并进入插值。

★ **精确定性是「工具与实现不对称」，不是「闸门不存在」**：

| 实现 | 反物理闸门 | 依据 |
|---|---|---|
| `scripts/analyze_bkl_curve.py`（**离线**） | ✅ **有且生效** | `max_drop()` `:134` ＋ `verdict_of()` `:159-161`；自检 **④ 有牙** |
| `TntgoBklCurve.kt`（**运行时**） | ❌ **有函数、零调用** | `grep` 仅定义 |

★★ 且**离线工具一开始就只对【放电】曲线施加这条闸门**（`verdict_of` 里 `max_drop` 只吃 `dis_levels`），
与物理语义一致 ⇒ **修法 = 把已有的正确判据补进运行时（只对放电），不是重新设计**。

⚠️ **不能直接把 `maxDrop()` 接进 `gate()`**：实测 `maxDrop(充电) = 647.5 mA`，而
**充电态 `|I|` 随亮度升高而下降是物理正确的**（`I_charge = 充电器供给 − 负载`），
`maxDrop()` 的拒绝方向**假设的是放电态** ⇒ 直接接线会**误杀正确的充电曲线**。

> ★ 本条与 ① 的验收**互相独立**：① 的结论不因本条而改变（本数据集放电曲线 `maxDrop = 0.0`，恰好单调）。
> **列为待办，未擅自改源码**（改源码需重建 ＋ 部署）。
