## 装之前请先读这三条

### 1️⃣ 装完还有**一步 adb 干不了**的活

Smartisan 的悬浮窗有**两道门**，脚本只能过第一道：

| 门 | 怎么过 |
|---|---|
| ① Android `SYSTEM_ALERT_WINDOW` appop | ✅ `adb` 可自动授 |
| ② **Smartisan 自己的悬浮窗授权** | ⛔ **只能人点**：`手机管理 → 权限管理 → Smartisan Powertoys → 悬浮窗` |

**只过 ① 不过 ② 的症状极具迷惑性**：窗口加得上、bounds 也对、
**logcat 一个错都没有 —— 但永远不显示。**

### 2️⃣ 「TNT GO 亮度」需要手动开**无障碍**

`设置 → 无障碍 → Smartisan Powertoys`。这是系统硬要求（`adb` 授不了）。

### 3️⃣ 「实时字幕」需要**你自己的** API Key

本应用**不含任何 Key**，也不会向作者回传数据。
去阿里云百炼（DashScope）申请一个，填进应用设置即可。
**不填只是该模块不工作**，不影响别的模块。

## ★ v0.3.0 相对 v0.2.0 改了什么

### 1️⃣ 「TNT GO 电量」的功耗数换成了**有依据的那一个**

这是本版最实质的变化。原先的功耗行**测不准**，原因是读数来自 UI 侧上报值，
而**真正决定电流的是 MCU 侧寄存器**。本版做了三件事：

| 改动 | 结果 |
|---|---|
| ★ 台账改存 **MCU 直读量**（`ui:mcu:mA:chg`），旧的 3 字段格式仍兼容解析 | 读数有了**唯一权威来源** |
| ★ **MCU 域相邻聚类分档 ＋ 档内取中位数** ⇒ 拟合 `\|I\| = a + b·MCU`，充/放各一条 | 曲线由**实测**得出，不是估的 |
| ★ **两道闸门（都能失败）** | ① **带外不外推**（超出实测档位只给最近端值并标「该处未测」）② **反物理拒绝**（更亮反而更省电 ⇒ 判「反物理」不采用） |

> ★★ **判定过程**：先测「亮度到底驱不驱动电流」——`separation = 30.94`（阈值 3.0）✓；
> 再用 **ABA 反转复现**（同亮度测两次）排除同期漂移；
> 最后**判定电流线性于 MCU 而非 UI**：实测 **1248 mA**，
> MCU 模型预测 **1238.6**（偏差 **0.3×MAD**）／ UI 模型预测 1584.2（偏差 **10.8×MAD**）⇒ **决定性**。
>
> ⚠️ **本版【还画不出完整曲线】** —— 需要用户在 **2–3 个亮度档各驻留 ≥2 分钟**才有 ≥2 个放电档位。
> 目前只有 1 个档，程序**正确地拒绝出曲线**（而不是硬外推一条假的）。

### 2️⃣ 电池容量学习**收敛得更可信**

`MIN_SEGMENTS` 2 → 3 ＋ 新增 **`MAD / 中位数` 离散度闸门**
（不用极差 —— 极差被两个极值主导）。
容量区在设置页改为**三态显示**：先验 N/3 段 ／ 已学习＋离散度 ／ ⚠️ 未收敛取保守值。

> ★ 实测：`容量 = 7047 mAh（已学习 5 段，取中位数，离散度 3.4%）`；
> 复算中位数 **7221 mAh**、离散度 **0.91%** ⇒ **阈值没有误杀真实数据**。
> ⚠️ 注意**先验值 10160 mAh 偏高约 30%**（网络来源，**已被实测证伪**）。

### 3️⃣ 两个 TNT GO 模块**不再抢串口**

新建共享库 **`:tntgo-serial`** ＝ 全工程**唯一**的 `openDevice` 入口
＋ **命令白名单** ＋ **跨进程文件锁**。

> ★★ **优先级是有意设计的**：电量侧 `lockWaitMs = 0`（拿不到**立刻让路**）／
> 亮度愿意等 3 s ⇒ **后台轮询给人手指让路**。
> 实机：让路 6 次 ／ 读失败 0 次 ／ 有害争抢 **0**，
> 且占用者**指名道姓**（`端口被「brightness-stream@…」占着 ⇒ 本轮让路`）。
> 长按路径延迟 `P50 = 33 ms / P95 = 42 ms`。

### 4️⃣ 🔴 修掉一个**会静默失效**的亮度心跳

**症状**：亮度的状态文件时间戳**看起来正常**、**logcat 一行异常都没有** ——
但心跳**从未被排程**，数值永远不会再更新。

> ★★★★ **根因**：心跳的**唯一排程点**写在 `if (root == null) { … }` 里，
> 而 `install -r` 重启后**无障碍服务先于 `onStartCommand` 连上** ⇒
> 走另一条路把状态文件**写了一次**，那一次性的写**恰好落进 90 s 新鲜度窗口**
> ⇒ **判据当场失效，而且失效方式是「让一切看起来正常」**。
>
> ⇒ ★★ 教训：**「文件里有一次写入」≠「发布者在心跳」**。

**修法**：① 排程移出 `if (root == null)`（`removeCallbacks` 保幂等）
② 心跳**每次留日志**（失败每次都记）③ 发布函数**返回布尔** ＋ 跳过时记**具名原因**
④ 失败原因拆成 `NoFile / Corrupt / Stale / IoError` 四种可行动状态
（★ 原来四种原因在日志里**长得一模一样**，害排查时**先怀疑错了方向**）。

### 5️⃣ 装了 3 个**会自己失败**的回归闸

| 工具 | 作用 | 自检 |
|---|---|---|
| `scripts/check_brightness_heartbeat.py` | **结构闸**：排程**不许**在 `if (root == null)` 内 ＋ 心跳必须留日志 | **4/4 有牙**（② 是原故障形态逐字复刻） |
| `scripts/analyze_bkl_curve.py` | 独立复算 ＋ 与盘上曲线**逐项对账** | **12/12 有牙**（含容差边界的**双向**证伪） |
| `scripts/bkl_common.py` | **解析只写一次**（治「两边各写一遍」） | — |

## ★ 关于「性能模式」：请不要期待它是万能加速

这一点值得单独说，因为它的实测结论**反直觉**：

| 场景 | 实测 |
|---|---|
| **AV1 软解**（无硬件解码器，纯 CPU） | ★ **+35.8%**，而且**方差被压掉**（20–32 fps → 42.2–42.7 fps）＝ **从卡到不卡** |
| **H.264 硬解 / Web / 多任务** | ★ **测不出收益**（CPU 92% 空闲；瓶颈在专用硬解器与磁盘 IO） |
| **空载** | ⚠️ **纯浪费**（+60 mA，约 +34%） |

⇒ **只在「持续 CPU 重负载」下开它**，而且用完就关
（应用内有自动过期机制）。

★ 另有一条被修正过的旧结论也留在这里：早期用**合成基准**测出的
「+75%」**不能外推到真实场景** —— 那正是上表第二行「测不出收益」的由来。

★ 还有一条**仍未解开**的：AV1 软解的收益**几乎全部来自 `POWER COLLAPSE`，不是抬频率**（已由直接测量排除热降频 /
运行队列等待 / 深 C-state 三个假说）。产品侧因此**只陈述事实、不写机理断言**。
