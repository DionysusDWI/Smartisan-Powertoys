# DSH 压缩崩溃诊断（`turn/end → compaction/prune → user/message → 进程死亡`）

> **版本**：v1.0 ｜ **创建**：2026-09-15 ｜ **状态**：✅ 已定位（**根因在 DSH 本体，不在本项目代码**）
> **触发者报告**：用户 2026-09-15「注意你的数据回收时间（结束时间）稳定触发了第二次 dsh 崩溃」

---

## 0 · 一句话

**DSH 宿主在「一轮结束 → `compaction/prune`（剪枝 ~2–4 万 token）→ 用户发来下一条消息」这个三点序列上会死。**
本会话已发生 **3 次**，形态**逐字节一致**，且 **token 规模在增大**（21,822 → 37,409 → 42,417）。

---

## 1 · 机械判据（一眼认出是不是这个病）

在会话归档里，**最后一条记录是 `user/message`，而其后直至重启都没有 `turn/start`**：

```
#… turn/end                       ← 上一轮正常结束
#… compaction/prune  tokens=NNNNN ← 剪枝
#… user/message  XXXB             ← 用户消息【已落盘】
   ★ 此后没有任何 turn/start / step/start  ⇒ 消息【从未被处理】
#… session/end-seed               ← 重启后重新播种
```

> ★ **区分点**：普通空闲也是「长时间没有记录」。**唯一可靠的判据是「用户消息落盘了但没被处理」** ——
> 光看间隔会把用户去吃饭误判成崩溃。

---

## 2 · 证据（3 次全命中，1 次对照）

| hub 重启时刻（UTC） | 之前 `compaction/prune` 的 token | 用户消息 | 消息被处理了吗 |
|---|---|---|---|
| `2026-09-15T09:05:05` | **21,822** | 741 B | ★ **没有** |
| `2026-09-15T13:08:43` | **42,417** | 799 B | ★ **没有** |
| `2026-09-15T13:21:55` | **37,409** | 967 B | ★ **没有** |
| `2026-09-15T12:05:15`（对照） | 无 prune | 无消息 | —（不适用） |

三次的**最后 6 条记录形状完全相同**，只有数字不同。对照那次没有 prune、没有待处理消息，也就没有崩。

**复现工具**：`.ref/20260915_dsh_session_probe.mjs <session.v3.jsonl.zstd> crash`
（自动读 `$DSH_HOME/profiles/web/hub.log` 的重启时刻并对齐会话记录）

## 4 · 根因判定

### 4.1 观察（实测，可直接复核）

- 崩溃点**固定在** `compaction/prune` 之后的第一条用户消息上。
- `compaction/prune` 已执行 **51 次**，而完整压缩（`compaction/start` → `/summary` → `/end`）**只在早期成功过 2 次**（`#2879`、`#5257`），**自 `#5260` 起再未成功**。
- 本会话规模：**14,305 条记录 / 54.9 MB（解压后）/ 15.9 MB（压缩）**，跨 **2 天**。
- 崩溃后的静止时长：**203 s / 355 s**（不是瞬间挂，是**卡死后被重启**）。

### 4.2 推断（★ 标注为推断，非实测）

**触发条件是会话规模。** 剪枝把 ~2–4 万 token 标为 shadowed 之后，下一条消息要据此**重新组装请求**；
规模越大这一步越重，最终卡死。**证据方向**：三次的 token 数**单调增大**，而同一天早先较小的那次
（21,822）静默 1,334 s 才重启、较晚的两次（42,417 / 37,409）只静默 203 / 355 s。

> ⛔ **未做的断定**：我没有读 DSH 的压缩实现去指认具体是哪一行。
> 本文件只主张**「症状—触发序列」这一层**已被三次独立实例钉死；**具体代码路径未核**。

### 4.3 为什么它会「盯上我的数据采集回合」

长采集回合是**单回合上下文增长最大**的那种（把 logcat／台账灌进来）。
它每次都会把 `compaction/prune` 推过临界 ⇒ **下一条用户消息正好撞上**。
所以这不是我在某条命令上写错了什么，而是**回合形态**的问题。

## 6 · 复现步骤（给 DSH 侧排查用）

```powershell
# 1. 找一个大型会话归档（每个 append 一个 zstd 帧，不是单帧）
$s = "$env:DSH_HOME\sessions\<workspace>\<session-id>\session.v3.jsonl.zstd"

# 2. 打印每次 hub 重启时会话记录停在哪、有没有「未处理的消息」
node .ref\20260915_dsh_session_probe.mjs $s crash

# 3. 看剪枝规模随时间的变化（关键：token 数在增长）
node .ref\20260915_dsh_session_probe.mjs $s prune
```

**给 DSH 维护者的最小线索**：`compaction/prune` 之后，`shadowedRange` 出现过
**`start > end`** 的反序（如 `{"start":13557,"end":12764}`、`{"start":14002,"end":13324}`），
且 `shadowedSeqs` 出现**跨代跳跃**（`13557, 12141, 12142, …`）。
这些反序记录**恰好都紧跟在一次重启之后** —— 可能是崩溃后重建剪枝状态时的边界情况。

## 7 · 工具与产物

| 文件 | 作用 |
|---|---|
| `.ref/20260915_dsh_session_probe.mjs` | 会话归档解码器 ＋ 崩溃对齐（`summary` / `prune` / `crash` / `last` 四个模式） |
| `PROGRESS-STATE.MD` §1.0 | 用户视角的处置入口 |

★ **解码器的一个坑（记下来免得重踩）**：`session.v3.jsonl.zstd` 是**逐次 append 的拼接帧**。
Node 的 `zstdDecompressSync` 与 `createZstdDecompress` **都只解第一帧就停**，
于是 15.9 MB 的档案只解出 **221 B**，**看起来像一个空会话** —— 必须按魔数 `28 B5 2F FD` 自己切帧。
